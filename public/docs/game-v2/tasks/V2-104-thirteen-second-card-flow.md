# V2-104 — Thirteen-Second Card Flow (Task Brief)

> Milestone: MVP-1 — Combat and Build Core
> Depends on: `V2-102` (accepted at `22a00d14`)
> Design contract: `docs/superpowers/specs/2026-08-21-threejs-gameplay-v2-design.md` §5.4
> Governing decisions: V2-ADR-007, V2-ADR-025, V2-ADR-039, V2-ADR-049…V2-ADR-055
> Live execution state: `docs/game-v2/PROGRESS.md`

## Done When

Reveal, countdown, input, timeout choice, pause, and resume are deterministic.

Concretely: a level-up generates a real, RNG-selected offer of up to three
distinct candidates (ability tier-ups and passive level-ups) instead of two
hardcoded choices; the offer and its seeded default pick are produced once,
at the tick the level-up triggers, so replay reproduces the identical offer
and the identical resolved choice regardless of real time elapsed; the
`/game-v2` card enforces a non-interactive reveal window, then a real
13-second wall-clock deadline with a visible last-5-second countdown; a
manual click/keypress or a real-time timeout both resolve through the same
runtime path.

**Out of scope, by `MASTER_PLAN.md`'s own split: reroll and banish are
`V2-105`.** This task's offer, once generated, is fixed until resolved.

## Scope

In scope:

1. A real offer: enumerate every offerable ability and passive identity
   (reusing `AbilityLoadoutSystem`/`PassiveLoadoutSystem`'s occupancy rules),
   pick up to three via the run's seeded RNG, and pick which one is the
   timeout default — all in one tick-bound step, so the result is
   authoritative `World` state, not presentation state.
2. Replacing the fixed two-string `RunCommand.choiceId` with an index into
   the current offer (`choiceIndex: 0 | 1 | 2`), and generalizing
   `resolveUpgrade` to apply whichever kind of candidate that index names.
3. The real-time card: a non-interactive reveal window, an interactive
   choosing window, a visible countdown for the last 5 of the 13 seconds,
   click and `1`/`2`/`3` keyboard input, and a real-time timeout that resolves
   with the pre-selected default exactly like a manual choice would.
4. Reduced-motion handling that changes only the reveal's visual treatment,
   never the 13-second deadline.

Out of scope:

- Reroll and banish (`V2-105`).
- The three starting weapons and the remaining ability/passive identities
  (`V2-106`, `V2-107`, `V2-401`) — MVP-1 still has exactly one ability and one
  passive identity, so a real offer can fill at most two of three slots
  today; the mechanism must be correct for three without requiring three real
  candidates to exist yet, mirroring V2-100/V2-101's injected-registry
  precedent.
- Any change to XP thresholds or `MVP0_MAX_PLAYER_LEVEL` — still one level-up
  per MVP-1 run.
- Exact numeric before/after damage copy on the card. §5.4 requires three
  visible cards, not specific wording; the card shows the candidate's kind,
  identity, and resulting tier/level generically, which is also what stays
  correct without per-ability display logic once `V2-106`/`V2-107` add
  identities with different effect shapes.

## Preflight Decisions To Record

- **V2-ADR-049 (proposed): the current offer is authoritative `World` state,
  not presentation state.** Two new strided `Uint8Array` stores
  (`offerCandidateKind`, `offerCandidateCode`, length
  `capacity * OFFER_CANDIDATE_COUNT`) plus one `offerDefaultIndex`
  (`capacity`) mirror the ability/passive slot pattern exactly
  (V2-ADR-036, V2-ADR-040), gated by a new `ComponentMask.LevelUpOffer` bit.
  Rationale: V2-ADR-025 forbids per-run state inside systems, and the offer
  must survive a checkpoint restore and hash identically between a live run
  and its replay — an offer held only in a system field or in React state
  would not.
- **V2-ADR-050 (proposed): the offer and its default pick are generated by
  one RNG-consuming step at the tick `pauseForLevelUp` fires, never
  re-derived later.** `LevelUpOfferSystem.generateOffer` shuffles the
  offerable pool with the run's `DeterministicRng` and also draws the default
  index in the same call. Rationale: the level-up phase does not advance the
  simulation tick, so a live run and its own replay must reach the resolved
  choice with an *identical* RNG state afterward regardless of how many real
  seconds a live player took. If the timeout path drew RNG again at the
  moment of timeout, that draw would happen at a real-time-determined instant
  no replay reproduces (replay never runs a real wall-clock timer), and the
  two runs' post-resolution RNG states would diverge. Pre-computing the
  default at generation time means resolution — by click or by timeout —
  never touches RNG again.
- **V2-ADR-051 (proposed): `RunCommand.choiceId: RunUpgradeChoiceId` becomes
  `choiceIndex: 0 | 1 | 2`, and `CommandRecorder` validates only that it is
  one of those three integers.** Rationale: the recorded command already
  captures the *resolved* choice; replay never needs to re-derive *how* it
  was reached (click or timeout), only *what* was chosen. An index is stable
  under RNG-shuffled candidate order and needs no registry lookup to
  validate, unlike a semantic string that would have to grow with every new
  identity.
- **V2-ADR-052 (proposed): `AbilityRegistry`/`PassiveRegistry` gain an `ids`
  getter (frozen, insertion-order array), and `AbilityLoadoutSystem` gains
  `isOfferable`/`addOrAdvanceTier` mirroring `PassiveLoadoutSystem`'s.**
  Rationale: offer generation must enumerate "every registered identity",
  which no registry currently exposes; the two loadout systems' occupancy
  rules already answer "is this identity offerable right now" for passives
  (V2-101) but not yet for abilities.
- **V2-ADR-053 (proposed): `ProgressionSystem` no longer depends on
  `WeaponSystem`.** Its only prior use of `WeaponSystem` was
  `advanceStarterTier`, which is exactly `AbilityLoadoutSystem.advanceTier`
  restricted to the starter slot. Calling the generic loadout method directly
  removes a needless indirection now that `resolveUpgrade` must apply
  arbitrary ability candidates, not just the starter weapon's.
- **V2-ADR-054 (proposed): the reveal/countdown/timeout timer lives entirely
  in the presentation layer (`game-v2/ui/LevelUpOverlay.tsx`), driven by a
  real interval independent of the simulation clock, and is never exercised
  by replay.** `ReplayRunner`/`replayToLevelUp`-style harnesses drive the
  runtime directly and apply a recorded `chooseUpgrade(choiceIndex)` at the
  right tick; they never run a real 13-second wait. This is consistent with
  V2-ADR-050: determinism is proved at the runtime layer, and the real-time
  card is a live-session affordance with no simulation authority.
- **V2-ADR-055 (proposed): the card shows a generic "kind + identity + next
  tier/level" label, not per-ability effect copy.** Reproducing exact
  before/after numeric copy generically across future ability shapes would
  need the offer system to know about `AbilityTierEffect`'s per-identity
  fields, which V2-ADR-044 deliberately keeps out of any shared pipeline. A
  generic label stays correct without per-ability display logic.

## Interfaces

```ts
// game-v2/contracts/LevelUpOffer.ts
export const OFFER_CANDIDATE_COUNT = 3;
export type OfferCandidateIndex = 0 | 1 | 2;
export type OfferCandidate =
  | Readonly<{ kind: 'ability'; identity: AbilityIdentityId }>
  | Readonly<{ kind: 'passive'; identity: PassiveIdentityId }>;
```

```ts
// game-v2/contracts/RunCommand.ts
export type RunCommand = Readonly<{
  tick: number;
  type: 'choose-upgrade';
  choiceIndex: OfferCandidateIndex;
}>;
```

```ts
// game-v2/systems/LevelUpOfferSystem.ts — stateless; World is authoritative
generateOffer(world, rng, owner): void
candidatesAt(world, owner): readonly (OfferCandidate | null)[] // length 3
defaultIndexOf(world, owner): OfferCandidateIndex | null
resolveIndex(world, owner, index): OfferCandidate // throws for an empty/invalid index
clearOwner(world, owner): void
```

## Steps

- [ ] **Step 1: World/replay layer (RED then implement)**

`LevelUpOffer.ts`, `RunCommand.ts`, `ComponentMask.ts`, `World.ts` stores +
`clearSlot`/`reset` wiring, `WorldSnapshot.ts` (schema 4),
`WorldStateValidator.ts`, `StateHasher.ts`, `WorldSnapshotWriter.ts`,
`CommandRecorder.ts`. Prove: offer stores clear on destroy/reset like
ability/passive; the validator rejects a kind/code mismatch and an
out-of-range kind; the hash changes when any offer byte changes;
`CommandRecorder` accepts only `choiceIndex ∈ {0,1,2}`.

- [ ] **Step 2: Offer generation and resolution (RED then implement)**

`AbilityRegistry`/`PassiveRegistry.ids`, `AbilityLoadoutSystem.isOfferable`/
`addOrAdvanceTier`, `LevelUpOfferSystem`, `ProgressionSystem` rewrite. Prove:
`generateOffer` never offers more than the offerable pool; the same seed
generates the same offer and default; `resolveIndex` throws for an
empty/invalid index without mutating anything; `resolveUpgrade` records
before applying only after validating the index resolves, applies ability
and passive candidates correctly, and clears the offer on resolution.

- [ ] **Step 3: Runtime wiring (RED then implement)**

`GameV2Runtime` (`abilityLoadoutSystem`\* already present from V2-103;
add `offerSystem`, thread `rng` into `progressionSystem.step`, rename
`chooseUpgrade`'s parameter, add `readout().levelUpOffer`),
`createMvp0Runtime.ts`, `ReplayRunner.ts`. Prove: the same recording replays
to the same offer and the same resolved choice at 30/60/120 FPS; a fresh
runtime and its own replay produce identical post-resolution RNG state.

- [ ] **Step 4: Presentation (RED then implement)**

`LevelUpOverlay.tsx` rewrite, `LevelUpOfferLabel.ts`, `GameV2App.tsx`,
`game-v2.css`. Prove (fake timers): input is inert during the reveal window;
the countdown becomes visible at exactly the last 5 seconds; a real-time
timeout with no manual input calls `onChoose` with the offer's default index
exactly once; a manual choice cancels the pending timeout.

- [ ] **Step 6: Mutation pass**

Mutants that must die: offer generation consuming RNG at timeout instead of
at generation time (breaks live-vs-replay RNG parity); `resolveIndex`
mutating before validating; the reveal window accepting input; the countdown
never becoming visible; the timeout never firing or firing more than once;
`CommandRecorder` accepting an out-of-range `choiceIndex`.

## Acceptance Criteria

1. A level-up generates a real offer of up to three candidates via seeded
   RNG, stored in `World`, hashed, checkpointed, and cleared like every other
   build fact.
2. The same seed and the same resolution (click or timeout) produce the same
   state hash across independent live and replayed runs, at 30/60/120 FPS.
3. The card enforces reveal → choosing → last-5-seconds countdown → timeout,
   with input inert only during reveal.
4. Reduced-motion mode changes only the reveal's visual treatment; the
   13-second deadline is identical either way.
5. Every gate in Step 5 passes and the mutation pass leaves no survivor.
