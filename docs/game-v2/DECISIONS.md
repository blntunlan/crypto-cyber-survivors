# Game V2 Decision Log

Decisions are append-only. A superseding decision references the old ID and
explains migration impact.

| ID | Decision | Reason |
|---|---|---|
| V2-ADR-001 | Build a clean Game V2 runtime rather than refactor the old gameplay runtime in place. | The old runtime contains overlapping authorities and insufficient gameplay foundations. |
| V2-ADR-002 | Keep the production demo on `main` until replacement gates pass. | Development must not remove the current playable product. |
| V2-ADR-003 | Use fixed top-down orthographic presentation in Three.js. | Preserve horde and telegraph readability while improving 3D visuals. |
| V2-ADR-004 | Use auto-target/auto-fire with manual movement, dash, and active abilities. | Concentrate player attention on positioning, timing, and build decisions. |
| V2-ADR-005 | Use four unified ability slots and six passive-stat slots. | Enforce build commitment and prevent every-run omnipotence. |
| V2-ADR-006 | Give every ability exactly three total tiers. | Keep progression legible, bounded, and ability-specific. |
| V2-ADR-007 | Pause simulation for a 13-second three-card slot reveal. | Preserve meaningful choices without allowing indefinite analysis. |
| V2-ADR-008 | Use Convergence to trigger a mandatory authored boss. | Make run length performance-sensitive but bounded and market-independent. |
| V2-ADR-009 | Offer cash-out after every boss; continuing risks the entire unbanked run balance. | Make greed a clear player-owned decision. |
| V2-ADR-010 | Support BTC, ETH, and SOL with locked LONG/SHORT and five leverage modes. | Preserve market identity while keeping the first asset scope bounded. |
| V2-ADR-011 | Resolve leverage through one versioned lethality profile. | Prevent enemy-damage and player-defense changes from multiplying twice. |
| V2-ADR-012 | Map each indicator profile through confirm, hysteresis, cooldown, and rearm states. | Prevent noisy market thresholds from spamming encounters. |
| V2-ADR-013 | Allow one primary encounter plus one support modifier. | Permit expressive combinations without unbounded event queues. |
| V2-ADR-014 | Reuse Railway market/indicator infrastructure only through a canonical adapter. | Preserve working infrastructure without importing legacy gameplay authority. |
| V2-ADR-015 | Keep direct token conversion outside the first vertical slice. | Separate gameplay proof from wallet, economy, security, and legal risk. |
| V2-ADR-016 | Treat the Agent Orchestrator as development infrastructure only. | Live gameplay and production authority must not depend on autonomous agents. |
| V2-ADR-017 | Deliver completed LEGO milestones with resume-safe repository checkpoints. | Large, interrupted work must remain understandable and restartable. |
| V2-ADR-018 | Select Game V2 at the root entry with an exact `/game-v2` lazy boundary. | The V2 route must not initialize legacy providers, debug side effects, or gameplay singletons. |
| V2-ADR-019 | Use direct Three.js with an owned typed-array ECS, RNG, and replay core. | React Three Fiber and external simulation libraries would add a second runtime authority before the core contracts are proven. |
| V2-ADR-020 | Keep `MASTER_PLAN.md` as stable task definitions and `PROGRESS.md` as live execution state. | Resume-safe tracking needs immutable acceptance criteria plus one unambiguous active-task checkpoint. |
| V2-ADR-021 | Resolve exact targeting distance ties by ascending slot order and give `TargetingSystem` no RNG at all, superseding the Task 12 interface line that reserved RNG for tie resolution. | Consuming RNG on geometric ties would make the replay stream depend on enemy positions every tick, so a 1-ULP float change would shift the whole sequence and break the V2-005 state-hash contract; ascending-slot is deterministic, allocation-free, and mutation-testable. |
| V2-ADR-022 | Give `WeaponSystem` ownership of projectile integration, lifetime countdown, and pool return in V2-011, leaving collision, damage, and death to V2-012. | Task 12 already produces `PROJECTILE_LIFETIME_SECONDS`; without an owner the constant is dead config and projectiles never return to the pool, while keeping damage in V2-012 preserves the one-authority rule. |
| V2-ADR-023 | The entity handle encoding `generation * capacity + slot` has exactly one owner, `World.entityIdOf(slot)`; `createEntity` returns through it, `capacity` stays private, and no consumer may re-derive the rule from a component-store length such as `world.masks.length`. | V2-011 re-derived the encoding in `TargetingSystem` and `WeaponSystem`, and `WeaponSystem` fed the re-derived id straight into `destroyEntity`, so any change to the encoding or store layout would have silently destroyed the wrong slot instead of failing loudly. One validating owner makes an out-of-range or retired slot throw `RangeError` at the boundary. |
| V2-ADR-024 | Give every player combat stat exactly one production writer: `CombatSystem.resetPlayer` owns health, max health, and radius, as `DashSystem` and `WeaponSystem` own theirs. | A constant that only test helpers assign produces a feature that is inert in production while the whole suite stays green; V2-012 shipped exactly that defect before review. |
| V2-ADR-025 | Game V2 systems hold no per-run state. Every run-scoped fact lives in a `World` store, and edge signals such as `CombatStepResult.playerDied` are derived from world state at step entry rather than latched in the system; `CombatSystem.reset()` is removed because nothing is left to reset. | `RuntimeCheckpoint` carries `World`, the RNG snapshot, lifecycle and tick — never system fields. A system that latched death locally would re-announce it after a checkpoint restore and fire the game-over transition twice, and each new system holding local state makes that class of desync harder to remove. |
| V2-ADR-026 | A system that reads a component must demand it in its own mask: `CombatSystem.step` requires `Body` because it measures contact overlap against `radius`, and rejects a player whose `maxHealth` is still zero. | Reading a store the mask does not require degrades silently — a `Body`-less player would have fought with a zero-radius hitbox, and an uninitialized player would read as permanently alive at zero health once the death signal became derived rather than latched. |
| V2-ADR-027 | Terminal player death dominates same-tick progression: `ProgressionSystem` clears its reusable output and ignores simultaneous kills, pickups, XP, and level-up work, while the owning runtime performs the terminal lifecycle transition. | `CombatSystem` can report both a lethal player hit and an enemy kill in one tick. Pausing for that kill's level-up before the runtime calls `endRun()` would leave the lifecycle in `level-up`, reject the terminal transition, and publish rewards from a run that already ended. |
| V2-ADR-028 | The runtime owns a deterministic enemy spawn cadence at the head of the fixed tick order, which the Task 15 step list did not name. `MVP0_ENEMY_SPAWN_INTERVAL_TICKS` is derived from the tier-one and tier-two kill periods rather than chosen. | Without a spawner there are no enemies, so V2-014's own acceptance criteria — kill, XP drop, level-up, death — are unreachable. Deriving the cadence from the two kill periods is what makes standing still lethal at tier one and survivable at tier two, so the first upgrade is the thing that buys back the run. |
| V2-ADR-029 | A reset run is a new session, not a bit-identical rerun, superseding the Task 15 Step 1 line that asked for a matching final state hash after `reset()`. Determinism is proven between independently constructed runtimes; the reset path is proven by replaying the same recording after a completed run and comparing every checkpoint field except `lifecycle.sessionEpoch` and `world.generations`. | Both exceptions are deliberate contracts, not drift: `GameV2Lifecycle.reset()` advances the session epoch and `World.reset()` retires the generation of every slot that was alive so a stale handle can never resolve. Demanding an identical hash across a reset would mean deleting one of those guarantees. |
| V2-ADR-030 | The simulation consumes the Float32 movement the recording stores: `GameV2Runtime` quantises the sampled intent with `Math.fround` before recording it and before any system reads it. | `InputRecorder` stores movement as Float32 while the sampled intent is Float64. Stepping the Float64 value made a replay diverge from the run it replayed by roughly one ULP per tick, which compounded into a different final state hash — the recording could not reproduce its own run. |
| V2-ADR-031 | An `IntentSource` may refuse a tick by returning `false`, and the runtime then leaves the tick counter untouched. | This is the mechanism behind the cross-FPS contract: render frame rate decides only how many fixed steps a frame earns, so a replay ends on exactly the recorded tick at 30, 60, or 120 FPS. Without it the driver would have to guess a frame count and would overshoot at every rate but 60. |
| V2-ADR-032 | The runtime exposes a cheap, hash-free `readout()` and a separate `debugSnapshot()` that adds the state hash; only the dev-only `window.gameV2Debug` surface uses the latter. | Hashing copies the entire world, so a HUD or test loop that polled a hash-bearing snapshot every frame would allocate a world copy per frame. Splitting them keeps the 60 Hz path allocation-light while leaving one canonical hash. |
| V2-ADR-033 | The simulation tick has exactly one owner, `GameV2Runtime.tick`. `SimulationClock` exposes `stepsAttempted`, not `tick`, and stops driving steps as soon as a step pauses it. | Once a step could be refused (V2-ADR-031) the clock’s counter stopped meaning “simulation tick”: it counts steps a paused, finished, or input-exhausted runtime discarded. Leaving it named `tick` with no production reader was a trap of exactly the kind V2-ADR-023 and V2-ADR-024 exist to close — the next HUD or telemetry wiring would have taken a silently wrong number. Draining the accumulator for refused steps also spent time the paused frame needed to hold its interpolation alpha. |
| V2-ADR-034 | `IntentSource` may implement `reset()`, and `GameV2Runtime.reset()` calls it. `KeyboardInput.clear()` is the production implementation. | The runtime cannot see inside its input adapter, and a source is not sampled at all while the run is over, so a dash pressed on the game-over screen was buffered and fired on the first tick of the next run. Because the restart reuses the run identity, that also broke the reproducibility a `?seed=` session promises. It additionally removes an undocumented obligation on every replay harness to reset its own cursor by hand. |
| V2-ADR-035 | The animation frame loop contains its own failure: a throw cancels the loop and surfaces the message, instead of repeating every frame. | The next frame is already scheduled by the time the body runs, so an uncaught throw spins at 60 Hz forever. The runtime has real, reachable failure modes — world capacity exhaustion above all, which the unbounded XP pickup lifetime makes a matter of run length — and a frozen game spraying the console is a worse outcome than a stopped one that says why. |
| V2-ADR-036 | Ability loadout state lives in `World` as two parallel `Uint8Array` stores of length `capacity * ABILITY_SLOT_COUNT`, addressed only through `abilityStoreIndex(slot, abilityIndex)`, which `World.abilitySlotIndexOf` wraps with range validation for live worlds, and a new `ComponentMask.AbilityLoadout` bit is required by every reader. | V2-ADR-025 forbids per-run state inside systems and `RuntimeCheckpoint` already carries `World`, so storing the loadout anywhere else would put build state outside checkpoint, replay, and reset. A fixed stride keeps slot order deterministic where entity-per-slot allocation would not, and giving the stride exactly one owner is the same guarantee V2-ADR-023 gives the handle encoding. The mask bit is V2-ADR-026: a reader must demand the component it reads. |
| V2-ADR-037 | Ability identities are hashed as stable numeric codes in `1..255` assigned by the registry, never as strings, and the empty slot is code `0`. A code is never reused once assigned. | The state hash must not move when an identity is renamed, and hashing one length-prefixed string per slot per hash would allocate on the path V2-ADR-032 deliberately keeps allocation-light. |
| V2-ADR-038 | Starter weapon damage is derived from the tier held in ability slot 0; the `World.weaponDamage` store is removed. `WeaponSystem.applyDamageUpgrade` becomes `advanceStarterTier`, and `AbilityLoadoutSystem.advanceTier` refuses to pass the identity's `authoredTiers`, which is `2` for `starter-projectile` until V2-102 authors tier 3. | V2-ADR-024: a loadout no production system reads is inert config that ships green, which is exactly the defect V2-012 shipped before review. Deriving damage also removes a second writable authority for the same fact. `authoredTiers` is what keeps the three-tier ceiling honest without inventing an unreachable tier-3 balance constant that no test could justify. |
| V2-ADR-039 | The ability registry is a validated value constructed by `createAbilityRegistry` and injected into `AbilityLoadoutSystem`, rather than a module-level table the system imports. | Four-slot occupancy cannot be tested with the single identity MVP-1 starts with, and the alternative — inventing placeholder identities in production config to make tests reachable — is the invented-constant failure `MVP0_SPAWN_FREE_SLOT_RESERVE` already cost once. Injection also makes V2-106 and V2-107 additive. |
| V2-ADR-040 | Passives get their own stores (`passiveSlotIdentity`, `passiveSlotLevel`, stride `PASSIVE_SLOT_COUNT`), their own `ComponentMask.PassiveLoadout` bit, and their own system rather than sharing the four ability slots. | Design §5.3 makes the six passive slots a capacity separate from the four ability slots. Sharing storage would let a passive consume an ability slot, which is exactly what §5.1 forbids, and would make the two ceilings — four slots with three tiers, six slots with five levels — one tangled rule. |
| V2-ADR-041 | `World.moveSpeed` is removed and player speed is derived from the `move-speed` passive level through an authored per-level table. | `moveSpeed` was already dead: no system read or wrote it and `MovementSystem` used the `PLAYER_MOVE_SPEED` constant directly, so it was a store that only the hash could see. Leaving it would have created a second candidate authority for the same fact the moment a passive changed speed — V2-ADR-038 applied to the second stat. |
| V2-ADR-042 | The MVP-0 level-up card gains a second fixed choice in V2-101 instead of waiting for V2-104. | V2-ADR-024: a passive loadout no production path can reach is inert config that ships green. The card stays paused with no reveal, no countdown, no timeout choice, and no reroll or banish, so it does not counterfeit the V2-104 contract — it only stops being single-option. |
| V2-ADR-043 | The simulation-to-scene axis mapping has one owner, `sceneZOf` in `game-v2/presentation/WorldToScene.ts`, and it negates: simulation `+Y` becomes Three `-Z`. | The top-down camera uses `up = (0, 0, -1)` so that `+X` stays on the right, which puts `-Z` at the top of the screen. Writing `worldY` straight into `z` therefore drew `+Y` downwards and `W` moved the player up in the simulation but down on screen. Negating in presentation was chosen over flipping the camera up vector, which mirrors X instead, and over flipping the input, which would redefine `+Y` as "down" in the simulation; presentation-only means no state hash, recording, or replay changes. |
| V2-ADR-044 | Each ability identity's tier effects are a typed, ability-specific shape (`AbilityTierEffect` is a union with one member type per distinct ability shape, discriminated by its own `ability` tag), not a shared numeric struct. `AbilityDefinition.tierEffects` is `readonly AbilityTierEffect[]`, index `tier - 1`, and the registry validates only its length against `authoredTiers` and each entry's own fields — not that the tag equals the owning identity's id, which would force every registry-driven test fixture to fabricate a real production identity instead of a local one. | Design §5.2 forbids "a universal damage and radius multiplier pipeline"; a shared struct with generic field names would be that pipeline wearing a different name. A discriminated union forces every new ability shape (`V2-106`, `V2-107`) to add its own effect type and forces every reader to switch on it exhaustively, so a reader that forgets a new shape fails to compile instead of silently reading `undefined`. |
| V2-ADR-045 | `starter-projectile`'s Tier 3 raises projectile radius (coverage) and shortens cooldown (cadence); it does not raise damage past Tier 2's value. | Design §5.2 assigns Tier 2 "damage and area/coverage" and Tier 3 "a stronger area/coverage behavior plus a modest cadence improvement" — Tier 3 is not specified to raise damage again. `STARTER_PROJECTILE_RADIUS_TIER_3 = 0.3` is half of `ENEMY_RADIUS`, keeping the combined collision radius at `0.9` against `0.2333` units of per-tick travel, so discrete collision stays sound by the same margin the Tier 1/2 radius already proves. `STARTER_WEAPON_COOLDOWN_TICKS_TIER_3 = 20` is two thirds of the base `WEAPON_COOLDOWN_TICKS = 30`, giving kill periods of 90/60/40 ticks across the three tiers at unchanged Tier 2 damage — a measurable, derived improvement rather than a chosen one. |
| V2-ADR-046 | `AbilityLoadoutSystem.tierEffectAt(world, owner, index)` is the single lookup path from a held slot to its tier effect; `WeaponSystem` calls it instead of importing an identity's tier-effect table directly. | `WeaponSystem` already takes an injected `AbilityLoadoutSystem` (`V2-ADR-039`'s injected-registry pattern). A second, independent path to the registry — a bare module import inside `WeaponSystem` — would let the two paths disagree about what a tier means, the same failure class `V2-ADR-038` closed for damage alone. |
| V2-ADR-047 | `GameV2RuntimeReadout` gains `abilitySlots: readonly (AbilitySlotReadout \| null)[]`, and `GameV2Runtime` takes an `AbilityLoadoutSystem` dependency to fill it — the same instance `createMvp0Runtime` already injects into `WeaponSystem`, not a second one. | `GameV2Runtime` had no path to ability-slot data; adding slot-generic HUD reads to `WeaponSystem` would be scope creep onto a system whose job is firing, not display. Sharing one instance keeps one authority for what a slot holds instead of two objects that could in principle disagree. |
| V2-ADR-048 | An `active` ability's displayed binding is derived from its slot index (`index + 1`) at read time; `AbilitySlotReadout` carries `index`, `activation`, and `tier`, never a precomputed label string. | Design §5.1 makes the binding the slot position, not a separately authored fact. Storing a label would create a second value that could disagree with `AbilityLoadoutSystem`'s own slot order; deriving it in one formatter (`AbilitySlotLabel.ts`) keeps exactly one rule. |
| V2-ADR-049 | The current level-up offer is authoritative `World` state: two strided `Uint8Array` stores (`offerCandidateKind`, `offerCandidateCode`) plus one `offerDefaultIndex`, gated by a new `ComponentMask.LevelUpOffer` bit, mirroring the ability/passive slot pattern exactly. | V2-ADR-025 forbids per-run state inside systems, and the offer must hash identically between a live run and its replay. An offer held in a system field or in React state would not survive a checkpoint restore or a hash comparison. |
| V2-ADR-050 | The offer and its RNG-seeded default pick are generated by one step at the tick `pauseForLevelUp` fires, and resolution — by click or by real-time timeout — never consumes RNG again. | The level-up phase does not advance the simulation tick, so a live run and its own replay must reach the resolved choice with identical RNG state regardless of real seconds elapsed. Replay never runs a real wall-clock timer, so an RNG draw made at the moment of a live timeout would happen at an instant no replay reproduces, diverging the two runs' post-resolution RNG state. |
| V2-ADR-051 | `RunCommand.choiceId: RunUpgradeChoiceId` becomes `choiceIndex: 0 \| 1 \| 2`; `CommandRecorder` validates only that it is one of those three integers. | The recorded command already captures the resolved choice; replay never needs to re-derive whether it came from a click or a timeout, only what was chosen. An index is stable under RNG-shuffled candidate order and needs no registry lookup to validate. |
| V2-ADR-052 | `AbilityRegistry`/`PassiveRegistry` gain a frozen, insertion-order `ids` getter; `AbilityLoadoutSystem` gains `isOfferable`/`addOrAdvanceTier` mirroring `PassiveLoadoutSystem`'s. | Offer generation must enumerate every registered identity, which no registry exposed; the ability loadout lacked the offerability and unified add-or-advance reads the passive loadout already had since V2-101. |
| V2-ADR-053 | `ProgressionSystem` no longer depends on `WeaponSystem`; it calls `AbilityLoadoutSystem.addOrAdvanceTier` directly. | Its only prior use of `WeaponSystem` was `advanceStarterTier`, which is exactly `AbilityLoadoutSystem.advanceTier` restricted to the starter slot. `resolveUpgrade` must now apply arbitrary ability candidates, not just the starter weapon's, so the indirection is removed rather than special-cased. |
| V2-ADR-054 | The reveal/countdown/timeout timer lives entirely in `game-v2/ui/LevelUpOverlay.tsx`, driven by a real interval independent of the simulation clock, and is never exercised by replay. | `ReplayRunner`-style harnesses drive the runtime directly and apply a recorded `chooseUpgrade(choiceIndex)` at the right tick; they never run a real 13-second wait. Determinism is proved at the runtime layer (V2-ADR-050); the real-time card is a live-session affordance with no simulation authority. |
| V2-ADR-055 | The level-up card shows a generic "kind: identity" label (e.g. "Ability: starter-projectile"), not a tier/level number or per-ability effect copy — `OfferCandidate` itself carries no tier/level field. | Reproducing exact before/after numeric copy, or even the resulting tier/level, generically across future ability shapes would need the offer system to know about `AbilityTierEffect`'s per-identity fields and an identity-keyed "current rank" lookup neither readout exposes, which V2-ADR-044 deliberately keeps out of any shared pipeline. |
| V2-ADR-062 | `AbilityDefinition` gains `startEligible: boolean`, validated as a real boolean by `createAbilityRegistry`. | The registry is the single source of truth for identity metadata (V2-ADR-039); a start-eligibility flag belongs there rather than in a second list a caller could drift out of sync with the registry itself. No pre-run selection UI reads it yet, matching how V2-ADR-039 accepted an uninstantiated registry shape before V2-106/V2-107 populated it. |
| V2-ADR-063 | `heavy-projectile` and `rapid-projectile` (V2-106's two new start-eligible identities) reuse `WeaponSystem`'s existing single-target auto-fire projectile pipeline unchanged, varying only their own `AbilityTierEffect` shape and tuning — not new firing mechanics such as a laser, drone, orbit, or salvo. | Building a genuinely new autonomous-weapon mechanic is comparable in size to the original V2-011/V2-012 work; V2-107's own scope ("the remaining five ability identities support active/AUTO four-slot combination tests") is where new mechanics and multi-slot combination belong. Reusing the proven pipeline keeps V2-106 bounded to registry content plus one lookup generalization while still shipping three real, separately-typed identities per V2-ADR-044. |
| V2-ADR-064 | `WeaponSystem` fires whatever identity occupies ability slot 0, not a hardcoded `STARTER_PROJECTILE.id` lookup; MVP-1's single autonomous firing slot stays fixed at index 0, and one shared `weaponCooldownTicksRemaining` store stays sufficient. | Three start-eligible identities that only a hardcoded starter-only lookup could ever fire would be the same "inert config" failure class V2-ADR-024/038/042 already closed once each. Generalizing the lookup (not the shared pipeline itself, per V2-ADR-063) is the minimum that makes "three start-eligible weapons" true of live combat, not only of registry data. MVP-1 never holds two autonomous weapons at once, so one cooldown store and one fixed slot index remain correct; per-slot cooldown storage is deferred to whichever task first makes two autonomous weapons concurrently live. |
| V2-ADR-065 | `resetPlayer` keeps assigning `starter-projectile` unconditionally to slot 0; a starting-weapon selection screen is out of scope and deferred with no task ID yet. | No master-plan task before MVP-4 names a title or character-select screen, and V2-106's Done-When requires only that three identities be start-eligible, distinct, and three-tiered — not that a player currently choose between them. Both new identities are proven live through direct system-level tests exercising the real generalized production path (V2-ADR-064) and through generic reachability via the existing level-up offer system (V2-105's `LevelUpOfferSystem` already enumerates every registered identity), with no offer-system change required. |
| V2-ADR-066 | The five `V2-107` mid-run-only identities (`needle-projectile`, `flicker-projectile`, `lance-projectile`, `cannon-projectile`, `siege-projectile`) reuse V2-ADR-063's exact single-target auto-fire pipeline and `AbilityTierEffect` shape, tuned as one multiplier `N` of `starter-projectile`'s own Tier 1 damage and cooldown (`damage = 10N`, `cooldownTicks = 30N`), with Tier 2/Tier 3 following the identical formula already established for `heavy-projectile`/`rapid-projectile`. | A single documented formula, tested once for all eight identities, is a stronger and cheaper proof than five independently-justified numbers, and keeps the "derived, not felt" requirement airtight. `N` (`1/10`, `1/5`, `3/2`, `5/2`, `4`) is chosen only so `30N` and `20N` stay integers and are pairwise distinct from `1`, `2`, `0.5`. |
| V2-ADR-067 | No `activation: 'active'` identity is registered in `V2-107`; all eight vertical-slice identities remain `auto`. | Design §5.1 names two categories, but only the autonomous category has a real, tested execution path today — no key-1..4 input pipeline exists anywhere in `game-v2/**`. Registering an active identity with an invented effect shape before any system could read it would repeat the "inert config" pattern V2-ADR-024/038/042/064 already rejected, with no consumer to even validate the shape against. The zero-`active`-content gap is real and explicitly deferred, not hidden. |
| V2-ADR-068 | `V2-107` leaves `resetPlayer` and `WeaponSystem`'s single-fixed-slot-0 firing model unchanged; it does not generalize `weaponCooldownTicksRemaining` to fire from more than one occupied `auto` slot concurrently. | This remains exactly the deferral V2-ADR-064 already recorded, with no task ID assigned. Each of the eight identities is proven individually correct and fireable through direct system-level tests (mirroring V2-106's own precedent), which is what `V2-107`'s Done-When requires — not that every identity be reachable through the live `resetPlayer` + level-up path. A related, previously unstated risk surfaced while scoping this task: because the offer system does not exclude a second `auto`-activation identity from being offered once one is already held, a player can already pick up e.g. `heavy-projectile` mid-run today and have it sit permanently un-fired in a non-zero slot — this was always latent in `V2-106`'s design, not introduced by `V2-107`, and is covered by the same deferral. |
| V2-ADR-069 | Enemy archetype identity is not stored per-entity; `EnemyDefinition` stats are written directly into `EnemySystem`'s existing `World` fields (`health`/`enemySpeed`/`contactDamage`/`radius`/`xpValue`) at spawn time and never read back as "which archetype." | Mirrors how a fired projectile's `AbilityTierEffect` numbers are baked into `projectileDamage`/`radius` with no "which ability fired this" store (V2-ADR-044/063). No system downstream of spawn needs archetype identity, only current stats; adding a store nothing reads would repeat the "component with no reader" pattern the codebase already avoids. |
| V2-ADR-070 | `V2-108` registers three enemy archetypes — `grunt` (unchanged MVP-0 baseline, cost `2`), `swarmling` (half health/damage/xp, `1.5x` speed, `0.75x` radius, cost `1`), `brute` (`1.5x` health/damage/xp, `0.6x` speed, `1.25x` radius, cost `2` — an equal-cost sidegrade, not a strict upgrade) — with `MVP0_ENEMY_SPAWN_BUDGET` fixed at `grunt`'s own cost. | A budget equal to `grunt`'s cost means drawing `grunt` or `brute` reproduces today's exact one-enemy-per-interval cadence exactly, and drawing `swarmling` spends the identical budget on two weaker enemies whose combined health and damage equal one `grunt`'s. This keeps MVP-0's calibrated balance (spawn interval vs. weapon kill-period) intact while making every archetype individually reachable within one budget window, without attempting a broader re-balance a bigger budget would force. |
| V2-ADR-071 | `EnemyComposer.compose` always consumes at least one RNG draw per non-zero-budget call, even when the outcome is deterministic in substance. | Skipping the draw when there is "no real choice" at the moment of the call would itself be state-dependent branching a replay would need to reproduce exactly, for a saving that does not recur in the production three-archetype budget. The accepted consequence — every downstream RNG-dependent outcome shifts for the rest of a run — was handled by re-selecting the fixed seeds that depend on it (`SCENARIO_SEED`, the e2e smoke's seed), matching the pattern already established when the ability registry grew (V2-106/V2-107). |
| V2-ADR-072 | `V2-109`'s 8–12 minute first-cycle Convergence envelope (design line 63) and the existing Tier 1/Tier 2 starter-weapon kill-period ratio both equal `1.5`, so one derived kill-count target (`CONVERGENCE_KILLS_TO_THRESHOLD = 480`) satisfies both envelope bounds exactly with no free parameter. | `480 * tier2KillTicks (60) = 28,800` ticks (8 min) and `480 * tier1KillTicks (90) = 43,200` ticks (12 min) both fall out of the same integer, pinned as an exact-equality config test rather than an approximate balance number, matching V2-ADR-070's "derived, not chosen by feel" bar. |
| V2-ADR-073 | `V2-109`'s per-player Convergence state (`convergence`, `convergenceReached`) lives in `World` as two new typed-array fields, not a separate non-ECS scalar or a new component mask bit. | Mirrors `xp`/`level`/`rerollCharges` — existing per-player progression state that already lives directly on the player's `World` row with no separate component gate, since every player entity always has it. Keeps `RuntimeCheckpoint`/replay/hash coverage automatic through the existing `WorldSnapshot` pipeline instead of requiring a second checkpoint-adjacent authority. |
