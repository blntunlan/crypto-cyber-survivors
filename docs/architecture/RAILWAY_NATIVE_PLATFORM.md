# Railway Native Platform

> **Status** live
> Owner: Core Engineering
> Created: 2026-06-13

## Purpose

This document defines the target backend platform for Crypto Survivors after removing Supabase from the runtime path. The project is still in beta, so the migration does not need to preserve every existing Supabase table or historical record. The goal is to build a clean Railway-native foundation that supports the current game and leaves explicit extension points for avatars, replay validation, coin audit, inventory, marketplace, and future live-ops systems.

The core rule is simple: the browser never talks directly to the database. The frontend talks to a versioned Railway API, and the Railway API owns authentication, authorization, validation, database writes, economy mutation, object storage access, and audit logging.

## Target Architecture

| Layer | Railway Component | Responsibility |
|---|---|---|
| Frontend | `frontend` service | React/Vite game client, static assets, HUD, screens |
| Public API | `api` service | Auth, profile, sessions, economy, inventory, replay, leaderboard |
| Database | `postgres` service | Railway Postgres as the only source of persistent relational truth |
| Market Runtime | `market-worker` or market aggregator service | Exchange ingest, indicator computation, market snapshots |
| Jobs Runtime | `jobs-worker` service | Cleanup, replay processing, reward reconciliation, scheduled audits |
| Object Storage | Railway bucket | Avatars, replay blobs, exports, moderation evidence |
| Admin Surface | `admin-api` or protected API routes | Economy inspection, moderation, operational repair tools |

The existing `railway-market-server` becomes the first version of the `api` service. It should keep its route structure, rate limiting, logging, health checks, and Postgres pool patterns, but Supabase-specific naming and runtime assumptions should be removed over time.

## Platform Rules

- All frontend calls go through `VITE_API_BASE_URL`.
- `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are removed from production builds.
- No client-side service can call Postgres, object storage credentials, or privileged endpoints directly.
- All mutable game outcomes are verified server-side before affecting wallet, leaderboard, inventory, or progression.
- All coin mutations are append-only ledger entries with idempotency protection.
- All upload flows use short-lived signed upload URLs generated by the API.
- All critical writes emit audit events for future reconciliation and admin review.
- All APIs are versioned under `/api/v1`.

## Domain Boundaries

| Domain | Owns | Future-Proofing Requirement |
|---|---|---|
| `accounts` | users, anonymous accounts, providers, devices | Can support email, OAuth, wallet, and anonymous upgrade flows |
| `profiles` | display names, public profile, avatar selection | Avatar storage is a reference, not a raw image column |
| `sessions` | game run lifecycle, start, finish, verification state | Supports replay-backed verification and market snapshot evidence |
| `economy` | wallets, ledger entries, rewards, purchases | Balance is derived or cached from append-only ledger entries |
| `inventory` | cosmetics, avatars, unlocks, shop ownership | Item catalog can evolve without schema rewrites |
| `replays` | replay metadata, storage object refs, validation status | Replay blob can be processed asynchronously by jobs |
| `leaderboard` | verified scores and seasonal rankings | Only verified sessions can enter ranked boards |
| `market` | price snapshots, OHLC, indicators, runtime context | Gameplay verification can reference immutable market snapshots |
| `audit` | security events, idempotency, suspicious behavior | Every economy and verification decision has traceable evidence |
| `telemetry` | client errors, performance, balance data | Non-critical and rate-limited, never blocks gameplay |

## Data Model Principles

Railway Postgres should start clean. Supabase schema can be used as reference material, but it is not the authority for the new model.

- Use UUID primary keys for player-facing entities.
- Use `created_at`, `updated_at`, and explicit status columns on lifecycle tables.
- Use `idempotency_keys` for payment-like, reward-like, and verification writes.
- Use `ledger_entries` as the durable economy source.
- Use `domain_events` or `audit_events` for operational history and future event-driven workflows.
- Use object storage keys for large assets instead of storing blobs in Postgres.
- Keep PII minimal and isolated from game economy data.
- Prefer additive migrations; destructive migrations require explicit beta reset approval.

## Economy And Coin Audit

Coin handling must be designed as a financial-style ledger even if the game economy is not real money.

- A session reward is calculated server-side from verified run facts.
- Session verification writes one `reward_claims` row and one or more `ledger_entries` in the same transaction.
- Reward claim retries reuse the same idempotency key and return the existing result.
- Purchases and unlocks debit through ledger entries, then write inventory ownership.
- Admin grants and rollbacks are ledger entries with actor metadata.
- `wallets.balance` can be a cached projection, but ledger remains the source of truth.
- Reconciliation jobs compare wallet cache against ledger totals and emit audit events.

## Replay And Validation

Replay support should be designed before every anti-cheat rule is finalized. The platform only needs stable extension points now.

- The frontend requests a replay upload intent from the API.
- The API returns a short-lived signed object storage URL.
- The frontend uploads the replay blob directly to Railway object storage.
- The frontend marks upload complete through the API.
- A jobs worker validates checksum, metadata, duration, score, and market snapshot consistency.
- Verified replays can unlock leaderboard eligibility, rewards, moderation evidence, or public sharing.
- Failed validations do not delete evidence automatically; they mark status and emit audit events.

## Avatar And Object Storage

Avatars and future file-backed systems should use the same object storage pattern.

- Public avatar catalog entries live in Postgres.
- Uploaded user assets use object storage keys and moderation status.
- The API controls upload size, MIME type, and ownership.
- The frontend never receives permanent write credentials.
- Image transformations or moderation can be handled by a future jobs worker.

## Market Runtime

Market data is gameplay-critical and must be treated as runtime evidence.

- The market worker owns exchange WebSocket connections.
- The worker writes current state and aggregate snapshots to Postgres.
- The API reads stable market snapshots for session verification.
- The frontend receives market state from the API, SSE, or dedicated market stream.
- Runtime evidence batches are persisted through `/api/v1/market/runtime-batch`.
- Session finish payloads should reference server-issued market context identifiers instead of trusting client-only price facts.

## Security Model

Railway-native security replaces Supabase RLS with explicit backend authorization.

- API middleware validates session tokens and resolves `account_id`.
- Route handlers enforce resource ownership.
- Admin routes require separate admin role claims and audit logging.
- Rate limits apply to auth, write, telemetry, leaderboard, and replay upload endpoints.
- Request bodies are schema-validated before database writes.
- Security-sensitive write routes require idempotency keys.
- Secrets live only in Railway environment variables.

## First Implementation Slice

The first slice should avoid avatar and replay complexity while establishing the architecture every future feature will reuse.

- Create a Railway-native schema migration for `accounts`, `profiles`, `game_sessions`, `wallets`, `ledger_entries`, `reward_claims`, `audit_events`, and `idempotency_keys`.
- Add API auth middleware for anonymous account tokens.
- Add `POST /api/v1/auth/anonymous`.
- Add `GET /api/v1/profile/me` and `PATCH /api/v1/profile/me`.
- Add `POST /api/v1/sessions/start` and `POST /api/v1/sessions/verify` with verification status support.
- Add `GET /api/v1/economy/wallet`.
- Add `POST /api/v1/economy/claim-run-reward` with idempotent ledger writes.
- Add frontend `ApiClient` and route only these flows through `VITE_API_BASE_URL`.
- Do not keep legacy provider paths in the runtime once Railway API smoke tests pass.

## Definition Of Done

- A fresh Railway environment can boot from migrations without Supabase.
- A new anonymous player can create a profile, start a session, finish a run, receive verified wallet credit, and see the wallet update.
- Reward claim retries are idempotent.
- All economy mutations produce ledger and audit records.
- Frontend production build contains no Supabase URL or anon key.
- API health check verifies database connectivity and required migration level.
- Supabase project downtime does not break gameplay, profile, economy, leaderboard, replay, or market runtime.
